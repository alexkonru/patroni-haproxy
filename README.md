# PostgreSQL 18 HA Cluster (Patroni + etcd + HAProxy)

Отказоустойчивый кластер PostgreSQL 18 на базе Debian 12 (QEMU/KVM): 3 узла баз данных с синхронной репликацией и аппаратным fencing (`watchdog`), а также 2 выделенных балансировщика HAProxy с клиентским переключением `libpq` multi-host.

---

## Архитектура

Стенд разделён на два независимых слоя (балансировка и хранение данных), чтобы исключить единую точку отказа (SPOF) как на уровне СУБД, так и на уровне маршрутизации клиентских запросов.

             |     lb-node1 (HAProxy)    |    |     lb-node2 (HAProxy)    |
             |      192.168.122.21       |    |      192.168.122.22       |
             +---------------------------+    +---------------------------+
                  |        |        |              |        |        |
                  |  TCP :5432 (PG) & HTTP :8008 (/primary, /replica?lag=10MB)
                  v        v        v              v        v        v
     +------------------+  +------------------+  +------------------+
     |     pg-node1     |  |     pg-node2     |  |     pg-node3     |
     |  192.168.122.11  |  |  192.168.122.12  |  |  192.168.122.13  |
     |                  |  |                  |  |                  |
     | PostgreSQL 18    |  | PostgreSQL 18    |  | PostgreSQL 18    |

### Узлы и ресурсы

Все виртуальные машины разворачиваются на базе образа Debian 12 (`generic`, полное ядро с драйверами аппаратного watchdog), используют тонкие Copy-on-Write диски `qcow2` и режим `cache=none` для честной работы `fsync()` без оседания записей в page cache хоста.

Точки входа для приложений (непривилегированный пользователь `appuser`, БД `appdb`):

* **RW (запись):** `host=192.168.122.21,192.168.122.22 port=5000 user=appuser dbname=appdb`
* **RO (чтение):** `host=192.168.122.21,192.168.122.22 port=5001 user=appuser dbname=appdb`
* **Статистика HAProxy:** `http://192.168.122.21:7000` и `http://192.168.122.22:7000`

## Ключевые инженерные решения

### 1. Консенсус (`etcd`) и изоляция дискового I/O
* Кластер `etcd` состоит из 3 узлов (протокол Raft, кворум $\lfloor 3/2 \rfloor + 1 = 2$), что позволяет пережить отказ 1 узла без потери управляемости.
* Поскольку `etcd` критически чувствителен к задержкам `fsync`, на каждом узле БД к каталогу `/var/lib/etcd` смонтирован отдельный виртуальный диск (`virtio-etcd-disk`, 1 ГБ, `noatime`, `cache=none`). Это снижает конкуренцию ввода-вывода с записью WAL и операциями `CHECKPOINT` в PostgreSQL.

### 2. Синхронная репликация и расчёт таймингов Patroni
В динамической конфигурации DCS заданы параметры:
* `ttl: 20`, `loop_wait: 2`, `retry_timeout: 5` — время жизни аренды лидера (leader lock) составляет 20 с, обновление происходит каждые 2 с. При мгновенной потере лидера перевыборы и переключение HAProxy укладываются в окно $\text{RTO} \le 25\text{ с}$.
* `synchronous_mode: true`, `synchronous_node_count: 1`, `synchronous_mode_strict: false` — лидер подтверждает `COMMIT` клиенту только после записи WAL на активный `Sync Standby`. При отказе одного узла это гарантирует $\text{RPO} = 0$. Если одновременно откажут обе реплики, кластер перейдёт в асинхронный режим ради сохранения доступности записи.
* `maximum_lag_on_failover: 1048576` (1 МБ), `use_slots: true`, `check_timeline: true` — исключают промоут сильно отставшей реплики и защищают от потери сегментов WAL за счёт слотов репликации.

### 3. Аппаратный fencing (`watchdog`) против Split-Brain
При сетевом разрыве живой процесс Patroni самостоятельно понижает локальный PostgreSQL в режим read-only. Однако при зависании самого процесса Patroni (например, из-за OOM, голодания CPU или `SIGSTOP`) он не способен остановить БД.
* К каждой ВМ БД подключено виртуальное аппаратное устройство `i6300esb` с действием `action=reset`, а через правила `udev` права на `/dev/watchdog*` выданы пользователю `postgres`.
* В Patroni задано `watchdog.mode: required` и `safety_margin: 5`. Без рабочего watchdog узел принципиально не может стать лидером.
* Таймаут аппаратного сброса равен $\text{TTL} - \text{safety\_margin} = 20 - 5 = 15\text{ с}$. Если Patroni перестаёт сбрасывать таймер, гипервизор принудительно перезагружает зависшую ВМ за 5 с до истечения аренды в `etcd`, физически исключая одновременную работу двух лидеров.

### 4. Автоматический возврат узла (`pg_rewind`)
* Включены `use_pg_rewind: true`, `wal_log_hints: on`, `full_page_writes: on` и контрольные суммы страниц (`initdb: data-checksums`), а также выделена отдельная роль `rewinder`.
* Когда бывший лидер возвращается в сеть после аварии и его ветка WAL расходится с новым `timeline`, Patroni автоматически откатывает изменённые блоки через `pg_rewind` вместо долгого полного клонирования `pg_basebackup`.

### 5. Маршрутизация HAProxy и клиентское переключение (`libpq`)
* Балансировщики `lb-node1` и `lb-node2` опрашивают Patroni REST API (`inter 1s fall 2 rise 2`): порт `5000` направляет трафик на узел с `GET /primary -> 200`, порт `5001` балансирует чтение (`roundrobin`) по узлам с `GET /replica?lag=10MB -> 200` (отсекая отставшие реплики).
* На обоих портах включена директива `on-marked-down shutdown-sessions`, мгновенно разрывающая существующие TCP-сессии к узлу при потере роли.
* Отказоустойчивость на уровне балансировщиков (без Keepalived/VRRP) реализуется нативной поддержкой списка хостов в `libpq`: при падении `lb-node1` клиентский драйвер автоматически переподключается к `lb-node2`.
* Клиентские запросы выполняются под непривилегированным пользователем `appuser`, чтобы рабочая нагрузка не исчерпала слоты `superuser_reserved_connections`, необходимые самому Patroni.

## Состав проекта и генерируемые файлы

В репозитории хранятся только исходные файлы:
* `deploy.sh` — скрипт полного развертывания сети libvirt, 5 ВМ, установки пакетов (с кэшированием APT между узлами БД) и настройки всех сервисов.

* `README.md` — документация проекта.

Артефакты, создаваемые локально при запуске `deploy.sh` и тестов (не должны попадать в Git):

* `pg-node{1..3}.qcow2`, `lb-node{1..2}.qcow2` — основные CoW-диски ВМ (хранят только отличия от базового образа).
* `pg-node{1..3}-etcd.qcow2` — отдельные диски по 1 ГБ под данные `etcd`.
* `seed-*.img` — FAT-образы `CIDATA` (2 МБ) для `cloud-init` (задают `hostname` и инжектируют SSH-ключ при старте ВМ).
* `lab_key`, `lab_key.pub` — сгенерированная пара SSH-ключей `ed25519` для управления ВМ.
* `__pycache__/`, `.pytest_cache/`, `.venv/` — служебные файлы Python.

## Требования и развертывание

### Требования на хосте
* Linux с поддержкой KVM, пакеты: `libvirt`, `qemu-full` (или `qemu-kvm`), `virt-install`, `dosfstools`, `acl`, `wget`, `openssh` (опционально `mtools`).
* Python 3.10+ для запуска автотестов.

### Запуск стенда

Полный цикл развертывания (создание сети, скачивание базового образа, запуск 5 ВМ, установка ПО, инициализация кластера и создание `appuser`/`appdb`):

```bash
chmod +x deploy.sh
./deploy.sh
```

Перенастройка конфигов и перезапуск кластера на уже созданных ВМ без пересоздания дисков:

```bash
./deploy.sh --configure-only
```

Проверка состояния кластера и устройств `watchdog`:

```bash
ssh -i lab_key root@192.168.122.11 "patronictl -c /etc/patroni/config.yml list"
ssh -i lab_key root@192.168.122.11 "ls -l /dev/watchdog*"
```

## Автотесты гарантий (`pytest`)

Установка зависимостей и запуск полного прогона:

```bash
python -m venv .venv
source .venv/bin/activate
pip install pytest "psycopg[binary]" requests
pytest -v -s test_guarantees.py
```

Все клиентские подключения в тестах выполняются от имени `appuser` строго через единую строку `host=192.168.122.21,192.168.122.22` (тесты не знают заранее, какой узел БД является лидером, и не подменяют адрес балансировщика вручную).

| Тест | Гарантия | Способ инъекции отказа | Критерии прохождения |
| :--- | :--- | :--- | :--- |
| `test_g1` | Маршрутизация HAProxy | Штатный режим | Оба HAProxy направляют `:5000` на единственного лидера (`pg_is_in_recovery() = false`); `:5001` распределяет чтение по обеим репликам (`pg_is_in_recovery() = true`). |
| `test_g2_and_g3` | $\text{RTO} \le 25\text{ с}$, $\text{RPO} = 0$ | `virsh destroy <leader>` под непрерывным потоком `INSERT` | Автоматический выбор нового лидера; простой записи $\le 25\text{ с}$; 100% подтверждённых транзакций сохранены в `tx_log` ($\text{RPO} = 0$). |
| `test_g4` | Возврат через `pg_rewind` | `virsh start <old_leader>` после фейловера | Узел возвращается в роли `replica`/`sync_standby` с `timeline > 1`; в `journalctl -u patroni -b` зафиксирован успешный запуск `pg_rewind`. |
| `test_g5a` | Защита от Split-Brain (сеть) | `iptables -I INPUT/OUTPUT -j DROP` между лидером и остальными узлами БД | Изолированный лидер снимает полномочия (`GET /primary != 200`) и блокирует локальную запись; оставшиеся 2 узла (кворум) выбирают нового лидера. |
| `test_g5b` | Watchdog Fencing (зависание) | `kill -STOP <patroni_pid>` на живом лидере (PostgreSQL остаётся запущен) | Аппаратный `i6300esb` принудительно перезагружает ВМ (смена `/proc/sys/kernel/random/boot_id` + маркер аварийного сброса в логе); одновременно не более 1 лидера; кластер восстанавливается. |
| `test_g6` | Отказоустойчивость HAProxy | `virsh destroy lb-node1` под непрерывным потоком `INSERT` | `libpq` автоматически переподключается к `lb-node2`; запись продолжается с $\text{RPO} = 0$; лидер БД не меняется. |

## Границы модели и допущения стенда

Для корректной интерпретации результатов на однохостовом KVM-стенде зафиксированы следующие рамки:
1. **Модель одиночного отказа для $\text{RPO} = 0$:** параметр `synchronous_mode_strict: false` обеспечивает нулевую потерю данных при потере 1 узла БД; одновременный выход из строя обеих реплик переводит оставшегося лидера в асинхронный режим.
2. **Совмещение `etcd` с узлами БД:** влияние дисковой нагрузки PostgreSQL на `etcd` минимизировано отдельным виртуальным диском и `cache=none`, однако в высоконагруженных промышленных инсталляциях кворум `etcd` выносят на 3 выделенных сервера.
3. **Общий источник времени (`kvm-clock`):** все ВМ синхронизированы от таймера хоста, поэтому сценарии рассинхронизации часов (clock skew) между узлами не моделируются.
4. **Сетевая фильтрация:** на узлах не включена закрытая политика фаервола (`INPUT DROP`) — `iptables` используется исключительно для эмуляции сетевого сплита в `test_g5a`, а разграничение доступа к БД обеспечивается через `pg_hba`.
5. **Скорость перезагрузки ВМ в `G5b`:** лёгкая KVM-машина после сброса по `i6300esb` способна загрузиться быстрее оставшихся 5 с `safety_margin` и законно переизбраться лидером на новом `timeline`. Корректность fencing подтверждается сменой `boot_id`, аварийным состоянием кластера при старте и инвариантом $\le 1$ лидера на всём интервале аварии.

## Очистка стенда

Удаление всех 5 виртуальных машин, их дисков и образов `cloud-init` (базовый образ `debian-12-generic-base.qcow2` сохраняется для быстрого повторного развертывания):

```bash
for vm in pg-node1 pg-node2 pg-node3 lb-node1 lb-node2; do
  sudo virsh destroy "$vm" 2>/dev/null || true
  sudo virsh undefine "$vm" --nvram 2>/dev/null || true
done
rm -f pg-node*.qcow2 lb-node*.qcow2 seed-*.img
```
